Deployment & security

Run the production image, scope Overseer to one project, and protect its privileged Docker access.

Container image

docker build -t overseer .
docker run --rm -p 8765:8765 \
  -v /var/run/docker.sock:/var/run/docker.sock \
  overseer

The image runs Gunicorn on port 8765 with one worker and eight threads and exposes a health check through GET /healthz. Stable releases publish AMD64 and ARM64 images with exact-version, major/minor, commit-SHA, and latest tags. Major tags are also published for versions 1.0.0 and above.

Compose project detection

When Overseer runs inside a Compose application, it reads the com.docker.compose.project label from its own container and lists other containers with the same label. Set an explicit project when automatic detection is not appropriate:

services:
  overseer:
    image: ghcr.io/pykhaled/overseer:0.2.0
    environment:
      OVERSEER_COMPOSE_PROJECT: my-application

When no project can be detected, Overseer lists every container visible through the configured Docker daemon.

Docker socket access

Treat Overseer as a trusted-administrator interface

A process with access to /var/run/docker.sock can inspect containers, mount host paths, and create privileged workloads.

  • Deploy Overseer only on trusted networks.
  • Put authentication and TLS at a trusted reverse proxy before allowing remote access.
  • Do not expose Overseer’s port directly to the public internet.
  • Avoid mounting the socket into unrelated containers.
  • Review lifecycle-route changes as security-sensitive code.

Overseer has no built-in authentication. Its CSRF header and project-scoped lifecycle checks do not eliminate the host-level risk of mounting the Docker socket.
