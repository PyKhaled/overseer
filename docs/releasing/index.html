Releasing

Prepare, publish, and verify semantic-versioned releases and multi-platform GHCR images.

Overseer publishes from GitHub Releases. A valid vMAJOR.MINOR.PATCH tag starts the release workflow, which reruns CI before publishing the container image to GHCR.

Prerequisites

  • The release commit is merged into main and its CI run is passing.
  • The version tag is unused and follows Semantic Versioning.
  • You can create releases and publish repository packages.

Prerelease suffixes such as v0.2.0-rc.1 are accepted. Build-metadata suffixes are not.

The canonical application version is in overseer/version.py. Update it before releasing; scripts and the release workflow reject a Git tag that does not match. The dashboard footer and health endpoint expose this version.

Prepare and publish

  1. Confirm all intended changes are on main.
  2. Choose the next semantic version and review commits since the previous release.
  3. Write notes that call out user-visible, breaking, and deployment changes.
  4. Create the tag against the exact commit that passed CI and publish the GitHub Release.
git fetch origin main --tags
RELEASE_COMMIT="$(git rev-parse origin/main)"
gh release create v0.2.0 \
  --target "$RELEASE_COMMIT" \
  --title "v0.2.0" \
  --generate-notes \
  --fail-on-no-commits

What gets published

For a stable v0.2.0, GHCR receives 0.2.0, 0.2, a commit-SHA tag, and latest. Prereleases never update latest. Images support AMD64 and ARM64 and include an SBOM, provenance, and attestation.

Verify the release

docker buildx imagetools inspect ghcr.io/pykhaled/overseer:0.2.0
docker pull ghcr.io/pykhaled/overseer:0.2.0
Never move a published version tag

If a published image is defective, document the problem and supersede it with a new patch version.
